Current State + Safer Target State

The live system already works: inquiry capture, email automations, PDFs/forms, payment, student portal, onboarding, readiness, reminders, and instructor briefings. The improvement path should preserve that working behavior and add visibility, state clarity, and safer automation around it.

White = existing capability Gold = manual / Joshua-dependent seam Coral = hole or risk Seafoam = strong foundation

Target state: same system, clearer state machine

1

Inquiry received

Capture need, date preference, course, contact, experience.

2

Needs qualification

Lightweight eligibility questions: age, swim, medical flag, prerequisite, gear.

3

Qualified + date proposed

Open seats shown. Grouping opportunities surfaced. Candidate knows next step.

4

Deposit requested

Seat still not held. Follow-up automation begins.

5

Seat reserved

Webhook confirms payment. Booking/event/student/inquiry link is canonical.

6

Ready student

Portal checklist complete. Student and Joshua both see readiness.

Holes and opportunities

High impact / low risk

Single canonical journey map

  • Document current states and allowed transitions.
  • Do not change live code first.
  • Use it to align email copy, admin labels, reminders, portal copy.
High impact / medium risk

Qualification fields before manual reply

  • Add age range, swim readiness, prior certification, gear status, medical flag.
  • Keep details out of marketing form.
  • Use answers to route, not auto-approve risky cases.
High impact / low risk

Seat-reservation language

  • Put “seat reserved after deposit” in calendar, inquiry confirmation, proposal, checkout, portal.
  • This reduces confusion without changing backend behavior.
Medium impact

Admin cockpit grouping

  • Needs reply.
  • Needs qualification.
  • Deposit pending.
  • Paid / onboarding incomplete.
  • Ready for course.
Medium impact

Email timeline audit

  • List every automated email, trigger, audience, and next CTA.
  • Find duplicate or contradictory CTAs.
  • Make portal the post-payment source of truth.
Medium impact

Knowledge base before chat agent

  • Build bounded answers for course fit, gear, logistics, forms, prep.
  • Escalate medical, refund, safety, edge cases.
  • Add agent only after state model is stable.
Medium impact

Readiness visibility

  • Student sees one checklist.
  • Joshua sees course roster readiness.
  • Reminders use the same readiness calculation.
Later

Post-course delight

  • Thank-you.
  • Certification path.
  • Saturday Sessions invitation.
  • Review/referral request.
  • Alumni conditions digest.
Risk

Hardcoded secrets/passcodes

  • Several admin/cron/passcode strings are in code/docs.
  • Worth fixing carefully, but not in same pass as journey UX.
  • Needs staged env-var migration to avoid breaking automations.

Recommended safe sequence

1. Map-only pass: produce current-state and target-state maps, plus email/form inventory. No runtime changes.
2. Copy-only pass: update language around deposit boundary and next steps. Low break risk.
3. Admin visibility pass: improve grouping/status labels without changing schema if possible.
4. Qualification pass: add lightweight fields to inquiry form and store them, behind careful defaults.
5. Secrets/auth pass: migrate hardcoded secrets to env vars only after inventorying every automation that depends on them.
